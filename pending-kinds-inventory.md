either genuinely consumed downstream, or carry a `# event-consumer:` marker
explaining why not. Two kinds in the current baseline are action-implying
(they represent an unresolved condition that reads as "something should have
happened next") but have no confirmed downstream consumer yet. Per the issue's
baseline-handling rule, these get `# event-consumer: pending #1364` markers as
an interim pointer rather than a blanket `audit-only` marking.

## Pending kinds

### `draft_pr_blocked`

- **Emission site:** `src/charlie_work/workflow.py:9454` (inside an `if`/`else`
  ternary alongside the sibling kind `janitor_gate`, which IS consumed).
- **Marker:** `# event-consumer: pending #1364 -- draft_pr_blocked has no
  automated consumer yet, only the query_events(kind=...) grep the comment
  above names; janitor_gate (the other branch) is separately consumed`
- **Why pending, not audit-only:** the surrounding code's own comment
  documents an intended ad-hoc `query_events(kind="draft_pr_blocked")` grep as
  the way to find these, i.e. the design already expects someone to look --
  there just isn't an automated consumer (heartbeat check, dashboard,
  escalation path) doing that look today. A PR left in draft because CI
  blocked it is exactly the kind of state that silently rots without a
  reconciliation pass.
- **Suggested remedy for the tracking issue:** add a `heartbeat_check.py`
  check (or a `query_events`-based reconcile-pass rule) that surfaces
  draft PRs blocked for longer than some threshold, mirroring how
  `janitor_gate` is already surfaced.

### `venv_editable_anchor_violation`

- **Emission site:** `src/charlie_work/supervise.py:1534`, inside the hard
  supervisor-refusal safety gate added for issue #974 (protects against a
  worktree's editable install silently repointing the main checkout's venv).
- **Marker:** `# event-consumer: pending #1364 -- hard supervisor-refusal
  safety gate (issue #974) with no confirmed alerting path beyond this log
  line + the refusal itself`
- **Why pending, not audit-only:** the refusal itself is the immediate
  safety action (the supervisor won't start against a corrupted venv
  anchor), but nothing today reads this event kind back out to alert an
  operator that the refusal happened. A supervisor that silently refuses
  to start and just sits there is close to indistinguishable from the
  supervisor being down for an unrelated reason (see the `agent liveness`
  and `supervisor heartbeat` memory lessons) -- someone needs paging, not
  just a log line.
- **Suggested remedy for the tracking issue:** add this kind to
  `scripts/heartbeat_check.py`'s classification (as an `error`-level,
  immediately-actionable check), since that script is already the
  standing "does anything read this back" mechanism named in AC5 of
  #1364.
